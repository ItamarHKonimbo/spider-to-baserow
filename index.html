מה זה ולמה צריך אותו

פלואו זה מקבל שם חנות/דיסטריביוטור של Spider-UI (למשל "ksp") ומייבא לתוך טבלת Baserow ייעודית את כל המוצרים ש-Spider גרד עבור אותה חנות, בכל הקטגוריות שבהן יש לה נוכחות — ללא קשר לקטלוג Medusa של לקוח כלשהו.

זה נבדל מהפלואו spider_youleap (spider.yaml): שם ההשוואה מתבצעת per-variant מול URL ספציפי שכבר קיים במטאדאטה של מוצר ב-Medusa. כאן אין Medusa בכלל — המטרה היא לבנות "מראה" מלאה של קטלוג חנות מתחרה כפי שהוא נראה ב-Spider, בטבלת Baserow עצמאית.

מוקדמות — מה צריך להיות מוגדר לפני הרצה

1. טבלת מיפוי חנות → טבלת פריטים

טבלה קבועה ב-Baserow (database 1011) ששומרת עבור כל חנות את מזהה הטבלה הייעודית שלה. Baserow API Tokens תומכים רק ב-Rows API ולא ב-ניהול סכימה (יצירת טבלאות/שדות) — לכן טבלה זו, וגם טבלת הפריטים של כל חנות, נוצרות ידנית מראש.

עמודהסוג שדהתיאור
store_nameSingle line textשם החנות/דיסטריביוטור, למשל ksp
table_idNumber (שלם)מזהה טבלת ה-items המתאימה בבייסרואו

2. טבלת פריטים לכל חנות ({store}-items)

נוצרת ידנית עם השדות הבאים, לפני הרצה ראשונה עבור אותה חנות:

עמודהסוג שדהמקור
skuSingle line textמפתח ייחודי לזיהוי/upsert
nameLong textתיאור/כותרת המוצר
priceNumber (עשרוני, 2 ספרות)מחיר נוכחי באתר
product_linkURLקישור לדף המוצר
categorySingle line textקטגוריית Spider שבה נמצא הפריט
brandSingle line textמותג
modelSingle line textדגם
spider_categorySingle line textשם קטגוריה כפי שמופיע ב-Spider (לעיתים בעברית)
last_updateDate (כולל שעה)מועד עדכון הפריט לפי Spider
last_seenDate (כולל שעה)מועד ההרצה האחרונה שבה הפריט נצפה

3. הרשאות

  • Spider API token: לקריאת categories, getdestributors, resultdestributor. גישה מוגבלת per-category/per-distributor — לא כל צירוף חנות+קטגוריה מורשה לאותו token, גם אם החנות מופיעה ברשימת getdestributors.
  • Baserow API token: Rows API בלבד (קריאה/כתיבה/עדכון שורות) — לא יצירת טבלאות/שדות.

תיאור הצמתים

1
get_categories

מה עושה: שולף מ-Spider את רשימת כל הקטגוריות הקיימות (דינמית, לא hardcoded).

API: GET https://spider-ui.rudenetworks.com/admin/v1/?method=categories&token=<API_TOKEN>

קלט: אין

פלט: מערך מחרוזות — שמות הקטגוריות (data.payload)

שפה: Bun/TypeScript

2
resolve_store_table

מה עושה: מוצא בטבלת המיפוי (3387) את מזהה טבלת ה-items המתאימה לחנות שהתקבלה בקלט.

API: GET https://table.konimbo.co.il/api/database/rows/table/3387/?user_field_names=true&filter__store_name__equal={distributor}, עם Authorization: Token <API_TOKEN>

קלט: distributor (מ-flow_input.distributor)

פלט: { table_id: number }

התנהגות בשגיאה: אם לא נמצאה שורת מיפוי לחנות — הצומת זורק שגיאה ועוצר את הפלואו (אין טבלת יעד לכתוב אליה).

3
לולאה על כל קטגוריה

מקור האיטרציה: results.get_categories (הרשימה מצומת 1)

הגדרות: parallel: false (רץ ברצף), skip_failures: true (כשל בקטגוריה אחת לא עוצר את הלולאה)

צומת פנימי — process_category

מה עושה: לכל קטגוריה — בודק תחילה אם החנות מופיעה ברשימת הדיסטריביוטורים של הקטגוריה, ורק אם כן שולף את הפריטים בפועל.

API שלב 1: GET .../?method=getdestributors&category={category}&token=<API_TOKEN>

API שלב 2 (רק אם החנות ברשימה): GET .../?method=resultdestributor&distributor={distributor}&category={category}&token=<API_TOKEN>

פענוח הנתונים: כל פריט מגיע כ-payload.outputs[].outputs[].values[] — מערך של אובייקטי {name, value}. הצומת ממפה: SKU→sku, DESCRIPTION→name, PRICE→price (מנוקה מתווים לא-מספריים), PRODUCTLINK→product_link, SPbrand→brand, SPmodel→model, SPIDERCATEGORY→spider_category, LASTUPDATE→last_update (מומר ל-ISO). פריט בלי SKU או PRODUCTLINK נזרק.

קלט: distributor (flow_input.distributor), category (flow_input.iter.value)

פלט: { category, skipped: boolean, reason?: string, items: Item[] }

מצבי skip:

  • החנות לא ברשימת getdestributors לקטגוריה — reason: "distributor_not_supported_in_category"
  • שגיאת API (כולל Access Denied) בכל אחת מהקריאות — reason מכיל את קוד/הודעת השגיאה מ-Spider
  • שגיאת רשת/חריגה — נתפסת ב-try/catch, reason מכיל את הודעת השגיאה
4
aggregate_results

מה עושה: מאחד את פלט כל איטרציות הלולאה למערך פריטים אחד, ומפריד רשימת קטגוריות שנכשלו בפועל.

לוגיקה: מרוקן/מדלג על מצב distributor_not_supported_in_category (זה לא כשל, רק היעדרות תקינה) — כל שאר ה-reason-ים מתועדים ברשימת failed_categories.

קלט: category_results (results.<loop_id> — מערך תוצאות מכל האיטרציות)

פלט: { items: Item[], failed_categories: {category, reason}[] }

5
upsert_items

מה עושה: לכל פריט — מחפש שורה קיימת בטבלת ה-items לפי sku; אם קיימת מעדכן (PATCH), אחרת יוצר שורה חדשה (POST). מרענן את last_seen לזמן ההרצה הנוכחית בכל מקרה.

זיהוי שינויים: לפני עדכון שורה קיימת, משווה את השדות (name, price, product_link, category, brand, model, spider_category, last_update) מול הערכים הקיימים בטבלה. שדות ששונו נאספים לרשומת changes (per-SKU, עם ערך ישן וחדש לכל שדה). last_seen עצמו לא נספר כשינוי — הוא מתעדכן תמיד.

API חיפוש: GET .../rows/table/{table_id}/?user_field_names=true&filter__sku__equal={sku}

API עדכון: PATCH .../rows/table/{table_id}/{row_id}/?user_field_names=true

API יצירה: POST .../rows/table/{table_id}/?user_field_names=true

קלט: items (results.aggregate_results.items), table_id (results.resolve_store_table.table_id), failed_categories (results.aggregate_results.failed_categories)

פלט (תוצאת הפלואו הסופית):

{
  total_items: number,
  inserted: number,
  updated: number,
  changes: { sku: string, fields: { field, old, new }[] }[],
  failed_categories: { category: string, reason: string }[]
}

הפעלת הפלואו

קלט להרצה: שם דיסטריביוטור, למשל {"distributor": "ksp"}.

הוספת חנות חדשה:

  1. יוצרים ידנית טבלת {store}-items חדשה ב-Baserow (database 1011) עם השדות המפורטים בסעיף המוקדמות.
  2. מוסיפים שורה בטבלת המיפוי (3387): store_name = שם החנות, table_id = מזהה הטבלה החדשה.
  3. מריצים את הפלואו עם distributor = שם החנות.

הפלואו אינו יוצר טבלאות או שדות אוטומטית — רק ממלא/מעדכן שורות בטבלה שכבר קיימת.
